Pourquoi l’asynchronisme
Dr. Mouna KARAJA
Cours développement d’applications réparties
131
La communication asynchrone joue un rôle central dans les applications réparties modernes.
Contrairement aux interactions synchrones, l’asynchronisme propose un modèle d’échange où les
processus n’ont pas besoin d’attendre une réponse immédiate pour continuer leur exécution.
→Ce modèle répond aux défis de la distribution, de la scalabilité et de la tolérance aux pannes.
→On parle de découplage temporel.
➢L’émetteur n’attend pas la fin du traitement.
➢Il envoie et continue son exécution.
➢Le retour (si nécessaire) arrive plus tard, via callback ou message de réponse.
✓le message peut être stocké,
✓transmis plus tard,
✓ré-essayé,
✓consommé par plusieurs acteurs.
L’asynchronisme est la base des architectures : orientées événements, basées sur des brokers de
messages, serverless avec déclencheurs, microservices distribués.

L’asynchrone permet de ne pas bloquer l’exécution, de continuer d’autres tâches pendant l’attente.
→Cela augmente la réactivité globale.
-

files/messages.

Le Message Passing est un modèle de communication asynchrone où un service (émetteur) envoie un
message à un autre service (récepteur) sans attendre de réponse immédiate.
→Ce modèle est utilisé dans : les architectures réactives et les microservices.
Caractéristiques principales :
➢Communication point-à-point : Le message a un destinataire unique. →Couplage spatial
➢Asynchronisme : L’émetteur n’attend pas la réponse : il continue son exécution immédiatement.
➢Message indépendant du protocole : Le message peut être envoyé via webSocket, socket réseau,
HTTP asynchrone, gRPC asynchrone, middelware, …
Si le récepteur est indisponible, le message peut être perdu

Modèle Publish / Subscribe
Dr. Mouna KARAJA
Cours développement d’applications réparties
138
Le modèle Publish/Subscribe est un modèle de communication asynchrone dans lequel les producteurs
(publishers) publient les messages dans un intermédiaire (souvent appelé broker, canal ou topic).
Les abonnés (subscribers) déclarent leur intérêt pour certains types de messages auprès de cet
intermédiaire.
Caractéristiques principales :
➢Découplage fort : spatial, temporel et logique.
➢Scalabilité.
➢Résilience.
➢Diffusion efficace (broadcast).
→Ce modèle est Idéal pour les architectures orientées événements (EDA).
Technologies majeures :
•
Redis Pub/Sub
•
Google Pub/Sub
•
Apache Kafka
Deux types principaux de Pub/Sub :
✓Pub/Sub basé sur les topics (Topic-based) où les subscribers choisissent
les topics. →Les messages sont publiés dans des topics nommés.
✓Pub/Sub basé sur le contenu (Content-based) où les abonnés spécifient
des filtres. →Le routage dépend du contenu du message.

Le streaming d’événements est un modèle dans lequel les événements générés par les systèmes (logs,
transactions, clics, mesures, signaux…) sont capturés, stockés et traités en continu sous forme de flux
(streams).
Dans ce modèle :
1.
les producteurs publient des événements dans un flux,
2.
les consommateurs lisent ces événements en continu,
3.
les événements sont persistés dans un journal (log) distribué,
4.
le traitement peut être temps réel ou quasi temps réel.
Contrairement aux systèmes classiques où les
données sont stockées puis traitées plus tard, le
streaming traite les données au moment où elles
arrivent.
→Les événements sont stockés dans un log
append-only (journal en écriture seulement).

Mécanismes fondamentaux
Dr. Mouna KARAJA
Cours développement d’applications réparties
141
Acknowledgements (ACK / NACK)
l’acknowledgement (ACK) est un accusé de réception envoyé par le consommateur au broker pour confirmer
qu’un message a bien été reçu et traité ; le NACK (negative ACK) indique un échec de traitement.
sans ACK, le broker ne sait pas si un message a été consommé correctement et risque de le perdre ou de le
supprimer prématurément.
Politique de réessai (Retry Policies) et backoff
→Règles qui déterminent combien et quand retenter la livraison d’un message en cas d’échec.
✓stratégie simple (n tentatives fixes)
✓exponential backoff (attente croissante : t, 2t, 4t…)
✓jitter (ajout d’aléa pour éviter les pics synchrones)
➔Après un nombre maximal d’essais, le message est envoyé en Dead Letter Queue.

Garanties d’ordre et partitionnement
L’ordering fixe les règles d’ordre de livraison et de traitement des messages, tandis que le partitionnement
divise un flux en sous-flux pouvant être traités en parallèle.
Le partitionnement permet de gagner en scalabilité mais au prix de l’abandon d’un ordre global strict. On
garantit alors seulement un ordre local à l’intérieur de chaque partition.
Durabilité des messages (persistance)
Capacité à stocker les messages de façon persistante (disque, log) pour survivre aux pannes.
→Pour éviter la perte d’informations en cas de crash du broker ou de la machine. 3 mécanismes utilisés :
messages en mémoire (volatile)
Messages persistants →écriture sur un support non-volatile (disque, log append-only)
Messages redondants →la duplication sur plusieurs nœuds indépendants pour assurer la tolérance aux
pannes.

Garanties de livraison des messages
Les systèmes de communication asynchrone offrent différents niveaux de garantie sur la livraison des
messages, selon le degré de fiabilité exigé par l’application.
•
Au-plus-une fois (At-most-once) :
Le message est envoyé sans mécanisme de réessai, donc il peut être perdu, mais il ne sera jamais livré
deux fois. →perte tolérable mais duplication inacceptable.
Exemple : Notification de logs
•
Au-moins-une fois (At-least-once) :
Le message est réémis tant qu’il n’a pas été confirmé (ACK), garantissant qu’il sera livré, mais il peut être
livré plusieurs fois. →Le consommateur doit donc être idempotent.
Exemple : Envoi d’un email de confirmation de commande.
•
Exactement-une fois (Exactly-once) :
Le système garantit que chaque message sera traité une seule fois, même en cas d’échec ou de
redémarrage. →La garantie la plus forte mais aussi la plus coûteuse.
Exemple : Traitement d’un paiement ou d’une transaction bancaire
