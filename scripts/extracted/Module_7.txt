===== PAGE 2 =====
Qu’est-ce que systemd ?
➢Définition:
systemd est le système d’initialisation et de gestion de services utilisé
par la majorité des distributions Linux modernes.
Il prend le rôle du processus PID 1, responsable du démarrage du
système et de la supervision continue des services.
➢
Fonctions principales
➢
Initialisation du système au démarrage
➢
Gestion et supervision des services (start, stop, restart, auto-restart)
➢
Gestion centralisée des journaux via journald
➢
Gestion des dépendances entre services
➢
Gestion de l’arborescence des cgroups
➢
Gestion des timers (alternative moderne à cron)

===== PAGE 19 =====
Dépendances systemd

Systemd permet de définir des relations entre unités via des directives.

Requires=
-
Dépendance forte :
Le service ne peut pas démarrer si l’unité référencée ne démarre pas.
Ex: Requires=network-online.target

Wants=
-
Dépendance faible :
Le service tente de démarrer l’unité liée, mais ne dépend pas de son succès.
Ex: Wants=sshd-keygen.service

Before=
-
Indique que le service doit être démarré avant une autre unité.

After=
Indique que le service doit démarrer après une autre unité.
Cela n’ajoute pas de dépendance, seulement une ordre de démarrage.

===== PAGE 20 =====
Que sont les Targets ?

Définition
Les targets sont des états prédéfinis du système gérés par systemd.

Rôle des targets:
-
Ils jouent le rôle moderne des runlevels de SysVinit.
-
Ils définissent quelles unités (services, sockets, devices,
mounts…) doivent être actives pour un état donné.
-
Permettent de passer rapidement d’un mode de
fonctionnement à un autre.
Un target = un ensemble d’unités décrivant un état global du
système.

===== PAGE 21 =====
Principaux Targets
Target
Rôle / Description

Mode multi-utilisateur sans interface graphique (équivalent
runlevel 3)
graphical.target
Démarrage avec serveur graphique + gestionnaire
d’affichage
rescue.target
Mode maintenance avec root shell et services minimum
emergency.target
Shell root ultra minimal, pas de services ; utilisé pour
réparations critiques

===== PAGE 23 =====
Changer le target par défaut

Modifier le mode de démarrage permanent
Pour définir un nouveau default target (affecte tous les prochains boots) :
sudo systemctl set-default multi-user.target
Explication:
-
Change l’état du système au prochain redémarrage
-
N’affecte pas l’état actuel
-
Utile pour :
▪
passer en mode console par défaut
▪
désactiver l’interface graphique
▪
forcer un serveur à démarrer en mode minimal
Attention: Passer en rescue.target ou emergency.target peut couper SSH et
services réseau.

===== PAGE 27 =====
— Analyse des fichiers Service

Structure générale d’un fichier .service
[Unit]
Description=Description du service
After=network.target
[Service]
Type=simple
ExecStart=/usr/bin/script.sh
Restart=on-failure
[Install]
WantedBy=multi-user.target

Role des sections
[Unit] →métadonnées, dépendances
[Service] →configuration du processus (comment lancer, gérer, redémarrer…)
[Install] →indique comment activer le service (enable)

===== PAGE 28 =====
— Paramètres importants

ExecStart=
Commande exécutée pour démarrer le service

ExecReload=
Commande pour recharger la configuration (si possible)

ExecStop=
Commande pour arrêter proprement


Politique de redémarrage
Exemples: on-failure, always, no


-

-

===== PAGE 29 =====
— Service personnalisé

Exemple minimal d'un service systemd exécutant un script shell

Fichier : /etc/systemd/system/backup.service
[Unit]
Description=Script de sauvegarde personnalisé
[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
[Install]
WantedBy=multi-user.target

Activation du service:
sudo systemctl daemon-reload
sudo systemctl start backup.service
sudo systemctl enable backup.service

A retenir
-
Type=oneshot car le script s’exécute puis se termine
-
Nécessite un daemon-reload après création ou modification
-
Très utile pour automatiser des tâches administratives

===== PAGE 30 =====
— Recharger systemd

Pourquoi recharger systemd ?
Lorsque tu crées ou modifies :
-
un fichier .service
-
un fichier .timer
-
ou toute unité systemd
— systemd ne détecte pas automatiquement les changements.

Commande indispensable
sudo systemctl daemon-reload

Effet:
-
Recharge toutes les définitions d’unités
-
Met à jour les dépendances
-
Ne redémarre aucun service

À retenir
Toujours exécuter daemon-reload après avoir créé ou modifier un fichier dans
/etc/systemd/system/ ou /usr/lib/systemd/system/

===== PAGE 33 =====
Gestion des Timers — Pourquoi
les timers ?

Pourquoi utiliser les timers systemd plutôt que cron ?
✓
Remplacent cron de manière moderne
Les timers offrent un solution native pour planifier des tâches, sans dépendre de crontab
✓
Logs intégrés automatiquement
Chaque exécution est enregistrée dans journalctl, ce qui facilite :
-
La traçabilité
-
L’audit
-
Le dépannage
✓
Dépendances systemd
Les Timers peuvent dépendre de targets, services, sockets…
→Permet de lancer une tâche seulement si le système est prêt
✓
Supervision automatique
Gestion des erreurs, relances automatiques, contrôle d’exit codes, protection de ressources (cgroups)

À retenir
— Les timers apportent robustesse, supervision, logs et intégration complète dans systemd.

===== PAGE 34 =====
— Anatomie d’un Timer 1/2

Les timers systemd se composent obligatoirement
de deux fichiers :
❑Fichier .service
Définit ce qui doit être exécuté.
Exemple : script, commande, programme,
sauvegarde…
Structure classique :
[Service]
ExecStart=/usr/local/bin/backup.sh

===== PAGE 35 =====
— Anatomie d’un Timer 2/2
❑
Fichier .timer
Définit quand le service doit s’exécuter
Exemple de base
[Timer]
OnCalendar=daily

Fonctionnement
Le .timer déclenche le .service
Les deux fichiers doivent porter le même nom :
-
backup.service
-
backup.timer

Avantage
Séparation claire entre:
-
la logique (service)
-
la planification (timer)

===== PAGE 36 =====
Exemple d’un Timer

Exemple complet : backup.service + backup.timer

Fichier: /etc/systemd/system/backup.service
[Unit]
Description=Script de sauvegarde automatique
[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh

Type=oneshot : exécution unique, pas de processus
permanent

Le script backup.sh contient la logique de sauvegarde

===== PAGE 37 =====
Exemple d’un Timer 2

Fichier : /etc/systemd/system/backup.timer
[Unit]
Description=Timer pour la sauvegarde quotidienne
[Timer]
OnCalendar=daily
Persistent=true
[Install]
WantedBy=timers.target

OnCalendar=daily →exécution chaque jour

Persistent=true →exécute la tâche si elle a été manquée
(machine éteinte)

-
Logs d'un service spécifique
journalctl –u ssh
Filtre uniquement les logs du service ssh.service
Trés utile pour diagnostiquer un service système
-
Logs du dernier démarrage
Journalctl –b
-
-b = boot
-
Montre tous les messages depuis le dernier démarrage
-
Option utile:: journalctl –b –1 →démarrage précédent

===== PAGE 41 =====
— Filtrage avancé
Filtrer par période
-
Depuis une heure/ un momdent précis
journalctl --since "1 hour ago"
journalctl --since "2025-02-18 08:00"
-
Jusqu'à un moment
journalctl --until "10 minutes ago"
Filtrer par priorité (sévérité)
journalctl -p err
Suivi en temps réel
journalctl -f

===== PAGE 42 =====
— Gestion de l’espace des
logs
-
Nettoyer automatiquement les journaux
-
Limiter la taille totale des logs :
sudo journalctl --vacuum-size=500M
→Conserve uniquement les 500 Mo les plus récents.
Limiter par date :
sudo journalctl --vacuum-time=7d
→Supprime les journaux plus vieux que 7 jours.
Limiter le nombre de fichiers :
sudo journalctl --vacuum-files=10
