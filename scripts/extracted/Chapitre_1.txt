Contexte et enjeux
Cours développement d’applications réparties
Le monde d’aujourd’hui est connecté. Les applications que nous utilisons tous les jours reposent toutes sur
un principe fondamental : elles sont réparties.
Cela signifie qu’elles ne s’exécutent pas sur une seule machine, mais sur un ensemble d’ordinateurs,
serveurs ou dispositifs qui coopèrent pour offrir un service unique, rapide, fiable et accessible partout
dans le monde.
Exemple : Facebook
➢Quand un utilisateur ouvre Facebook, il accède à une interface sur son smartphone ou son navigateur.
➢Les données de son profil (amis, publications, photos) sont stockées dans différents serveurs répartis
dans le monde.
➢Quand il publie une photo, cette photo est envoyée à un serveur de stockage, répliquée dans plusieurs
centres de données (pour la sauvegarde et la rapidité d’accès), et rendue disponible à ses amis à travers
d’autres serveurs.
➢Quand il like ou commente, l’information passe par d’autres serveurs qui mettent à jour la base de
données et notifient instantanément ses amis.
→Pourtant, pour l’utilisateur, Facebook semble être une seule application fluide.

Cours développement d’applications réparties
applications réparties = applications distribuées
✓Les composants peuvent être des programmes, des bases de données, des services web, etc.
✓Ces composants sont géographiquement dispersés, mais ils travaillent comme un tout.
✓L’utilisateur ne perçoit pas cette répartition : il a l’impression d’interagir avec une seule application.
Une application répartie est une application dont les composants logiciels s’exécutent sur plusieurs
ordinateurs (ou nœuds) reliés par un réseau, et qui coopèrent pour fournir un service unique et cohérent
à l’utilisateur final.

Qu’est ce qu’un système réparti ?
Un système réparti est un ensemble de machines autonomes reliées par un réseau, qui coopèrent pour offrir
l’illusion d’un système unique et cohérent.
Caractéristiques :
✓Les ressources (processeurs, mémoire, données) sont distribuées.
✓Les utilisateurs interagissent comme s’ils accédaient à une seule machine centrale.
✓Les communications passent obligatoirement par un réseau.
Exemple : un cluster de serveurs qui hébergent un moteur de recherche comme Google.

Les applications réparties
➢Elle est composée de services (authentification, messagerie, paiement, etc.).
➢Chaque service peut être hébergé sur une machine différente, mais l’ensemble coopère pour offrir une
application cohérente.
➢Ces services doivent être accessibles via des interfaces bien définies. Ces interfaces peuvent prendre
différentes formes, telles que des API ou des protocoles de communication.
Une application répartie n’est pas un bloc monolithique :
Dans les applications réparties, on distingue souvent :
➢Les services représentent les fonctionnalités offertes (par exemple : authentification, messagerie).
➢Les interfaces représentent le moyen par lequel ces services sont accessibles.
C’est comme un contrat qui définit :
–
Quelles opérations on peut demander au service (ex. : s’authentifier, envoyer un message, publier
un contenu).
–
La manière dont ces opérations doivent être appelées (ex. : via un protocole HTTP, une API REST, un
message JSON).

Cours développement d’applications réparties
Exemple : Facebook propose plusieurs services répartis : le service d’authentification, le service de
messagerie instantanée, le service de publication et partage de contenu, le service de recherche, etc.
Dans un système réparti, un service peut être offert par plusieurs serveurs et consommé par plusieurs
applications.
Les applications réparties
❖Le service d’authentification permet à l’utilisateur de se connecter.
❖Son interface définit les règles :
✓Quelles données envoyer ? (login, mot de passe)
✓Comment les envoyer ? (par un formulaire Web, ou via une API pour une application mobile)
✓Ce que le service renvoie ? (succès ou erreur)
→Ces services, bien que physiquement répartis, apparaissent à l’utilisateur comme une seule application.
Ainsi, même si les services sont physiquement répartis (hébergés sur différents serveurs), l’utilisateur y
accède toujours de la même manière grâce à leurs interfaces bien définies.

Le génie logiciel appliqué aux systèmes répartis exige des approches spécifiques (patrons d’architecture,
middlewares, protocoles de communication, etc.).
Les systèmes répartis modifient profondément la manière de concevoir et développer des logiciels :
• Latence, panne réseau, sécurité des communications
Nouvelles contraintes
• Apparition des modèles client-serveur, microservices,
services web.
Architectures logicielles
• Nécessité de penser en termes de scalabilité,
tolérance aux pannes, réplication de données.
Méthodologies
• Conception modulaire pour faire évoluer l’application
sans arrêter tout le système.
