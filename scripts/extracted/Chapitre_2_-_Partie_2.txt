Les protocoles de la couche « application »
La couche « application » est la plus haute du modèle TCP/IP. Elle permet la communication directe entre les
programmes utilisateurs (navigateur, client mail, messagerie instantanée, etc.).
Elle définit les protocoles applicatifs, c’est-à-dire les règles de dialogue entre applications sur deux machines.
Chaque protocole utilise un numéro de port pour être identifié par la couche transport (TCP/UDP).
Qu’est ce qu’un numéro de port ?
Un numéro de port est un identifiant logique (un nombre) utilisé par le système d’exploitation pour
distinguer les applications qui communiquent sur le réseau.
→Il sert à diriger les messages vers le bon programme à l’intérieur de ton ordinateur.

Mécanismes de communication bas niveau
Un socket est le couple (adresse IP, port) →il identifie une application précise sur une machine.
Les communications TCP ou UDP sont identifiées par le quadruplet
(IP_client, Port_client, IP_serveur, Port_serveur).
➢Une socket est une interface logicielle (un point d’accès) entre l’application (couche
application) et le protocole de transport (TCP ou UDP).
Qu’est ce
qu’une
socket ?
➢Elle permet à un programme d’envoyer et de recevoir des données comme s’il écrivait
dans un canal de communication.
➢La socket est la “porte” par laquelle les données d’une application sortent pour entrer
dans le réseau (et inversement).
→Ce couple forme un socket endpoint unique sur une machine.
Il faut distinguer deux types principaux de sockets, selon le protocole de transport utilisé :
✓les sockets TCP,
✓et les sockets UDP, basées sur l’échange de datagrammes.

Les sockets TCP
Le protocole TCP est orienté connexion. Avant tout échange, une connexion fiable est établie entre le client
et le serveur. Les données circulent ensuite sous forme de flux continus, garantissant :
✓la livraison des données sans perte,
✓le respect de l’ordre d’envoi,
✓et la fiabilité de la communication.
1.
Le serveur crée un objet ServerSocket et se met en attente d’un client sur un port précis.
2.
Le client crée un objet Socket et tente de se connecter à ce port.
3.
Une fois la connexion acceptée, les deux programmes peuvent échanger des données en utilisant des
flux (InputStream et OutputStream).
4.
À la fin, les sockets sont fermées.
En java, les classes utilisées sont :
✓ServerSocket : utilisée côté serveur pour écouter les connexions entrantes sur un port donné.
✓Socket : utilisée côté client (et aussi côté serveur après acceptation) pour établir la connexion et
échanger les données (lecture/écriture via des flux).

Les sockets UDP
Le protocole UDP est non orienté connexion. Il n’établit aucune connexion préalable entre le client et le
serveur. Les données sont envoyées sous forme de datagrammes indépendants : chaque paquet circule
séparément dans le réseau, sans garantie d’ordre ni de réception.
1.
Le serveur UDP crée un DatagramSocket et attend la réception d’un paquet.
2.
Le client UDP crée également un DatagramSocket et envoie un DatagramPacket vers l’adresse et le port
du serveur.
3.
Chaque message envoyé est indépendant des autres →il n’existe aucune session ni connexion
persistante.
4.
Après réception, le serveur peut répondre via un autre datagramme.
Fonctionnement :
En java, les classes utilisées sont :
✓DatagramSocket : représente la « prise » de communication pour envoyer ou recevoir des datagrammes.
✓DatagramPacket : représente le paquet de données à transmettre (il contient les données, l’adresse IP
du destinataire et le port).

Bas niveau VS. Haut niveau
Avec la complexité croissante des applications distribuées, les développeurs ont cherché à :
✓Simplifier la programmation réseau,
✓Automatiser la gestion des échanges (marshalling, transport, erreurs),
✓Rendre la communication transparente (comme un appel local),
✓Assurer l’interopérabilité entre systèmes et langages.
Rappel : mécanismes de communication bas niveau (les sockets)
Avantage : contrôle total, performance.
Inconvénient : code complexe, risque d’erreurs, couplage fort entre client et serveur.
Le programmeur gère : •
la création de la connexion (adresse IP, port) ;
•
l’envoi/réception de flux d’octets ;
•
le format des messages (encodage, protocole applicatif).
D’où la naissance des mécanismes de communication haut niveau.

Mécanismes de communication haut niveau
Un mécanisme de communication haut niveau est une abstraction logicielle qui permet à des composants
répartis de communiquer sans gérer directement les détails bas niveau du réseau (sockets, ports, formats
binaires, etc.).

programmation plus intuitifs et plus proches des concepts métier. →Le programmeur interagit via des
objets, des procédures, des services, ou des messages structurés au lieu de manipuler des flux d’octets.

RPC (Remote Procedure Call)
Les RPC apparaissent comme une abstraction qui permet au développeur d’appeler une procédure (ou
méthode) située sur une autre machine comme s’il l’appelait localement. L’objectif est de masquer la
complexité du réseau et de rendre la programmation distribuée plus proche de la programmation locale.
Pourquoi RPC ?
Abstraction
Productivité
Lisibilité et
maintenance
Interopérabilité
Principe de base du RPC :
1.
Le client appelle une fonction “comme d’habitude”.
2.
Le système RPC prépare l’appel et l’envoie au serveur.
3.
Le serveur reçoit la demande, exécute la fonction demandée.
4.
Le résultat est renvoyé automatiquement au client.
5.
Le client récupère le résultat comme s’il venait d’une fonction locale.

✓Marshalling / Serialization : conversion des paramètres en une représentation binaire (Protobuf,
Thrift) ou textuelle (JSON, XML) pour transport.
✓Unmarshalling / Deserialization : reconstitution des paramètres à l’autre bout.

Transition historique : RPC →CORBA →RMI
Lorsque le RPC (Remote Procedure Call) a été inventé dans les années 1980, la majorité des langages
utilisés (comme C, Pascal, Ada) étaient procéduraux.
Avant que Java n’existe (1995), l’OMG (Object Management Group) a conçu un standard appelé :
CORBA – Common Object Request Broker Architecture (début des années 1990).
Permettre à des programmes écrits dans différents langages (C++, etc.) de communiquer entre eux, en
appelant des méthodes d’objets distants de manière transparente.
Les systèmes distribués devaient eux aussi évoluer pour permettre l’appel de méthodes sur des
objets distants, pas seulement de fonctions.
On appelait donc à distance des fonctions ou procédures, pas des objets.
Mais à la fin des années 1980 et au début des années 1990, la programmation orientée objet (POO) s’est
imposée (C++, Smalltalk, puis Java).

Transition historique : RPC →CORBA →RMI
CORBA est une extension orientée objet du RPC :
1.
Définition des interfaces dans un langage neutre appelé IDL (Interface Definition Language).
2.
Compilation de l’IDL pour générer automatiquement les stubs (côté client) et les squelettes (côté
serveur).
3.
Le client appelle une méthode sur l’objet distant via le stub, comme s’il s’agissait d’un objet local.
4.
L’ORB (Object Request Broker) se charge de transporter la requête au serveur et de gérer la
communication réseau.
5.
Le serveur reçoit l’appel via le squelette, exécute la méthode et renvoie le résultat au client à
travers l’ORB.
CORBA a eu un grand succès dans les années 1990, étant donné qu’il visait une interopérabilité multi-
langages, mais :
✓Il était complexe à configurer ;
✓Il nécessitait beaucoup de fichiers et de couches pour faire de simples appels.
L’ORB joue exactement le même rôle que le RPC Runtime dans un système RPC classique. il est
l’intermédiaire qui s’occupe de toute la mécanique réseau entre le client et le serveur.

La naissance de RMI (Remote Method Invocation)
Le but du RMI est donc :
✓de permettre la communication entre objets Java distribués sur un réseau,
✓tout en conservant les principes de la programmation orientée objet (encapsulation, héritage,
polymorphisme…),
✓et en cachant complètement la complexité du réseau au développeur.
Les ingénieurs de Sun Microsystems se sont inspirés du modèle CORBA, mais ont voulu un système :
✓Plus léger,
✓Spécifique à Java,
✓Utilisant la sérialisation native des objets Java.
RMI : Un mécanisme purement Java, inspiré de CORBA, qui permet d’invoquer une méthode sur un
objet situé sur une autre machine Java, comme si l’objet était local.
Quand Java est apparu (vers 1995), il a apporté un modèle objet simple et uniforme, et une machine
virtuelle (JVM) garantissant la portabilité.
C’est ainsi qu’est né RMI
(Remote Method Invocation)
