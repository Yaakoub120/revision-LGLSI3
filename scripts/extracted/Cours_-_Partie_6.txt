Architecture de Kubernetes
260
Orchestration des conteneurs
Pod
Groupe de containers déployés ensemble
Les containers du Pod :
Sont toujours démarrés, arrêtés et répliqués en
groupe
Partagent le même Nework, Namespace, IP et
Ports
Peuvent communiquer ensemble (un conteneur
peut contacter un autre sur le même pod) en
utilisant localhost
Peuvent partager des données via des shared
volumes
Le Pod est l'entité de base qu’on va répliquer et
qu’on va mettre sur différents nœuds du cluster.

Orchestration des conteneurs

C’est le fichier dans lequel on décrit l’architecture
cible que l’on veut atteindre.
Les conteneurs qu’on veut mettre dans le Pod
Les détails de réplication
Les stratégies qu'on va utiliser pour les mises à jour

Dans cet exemple:
Un déploiement nommé nginx est crée, indiqué par le champ

Le modèle de pod, ou le champ spec: template, indique que

Ouvrez le port 80 pour envoyer et recevoir du trafic

===== PAGE 14 =====
Service
264
Orchestration des conteneurs
Permet d'accéder à un groupe de Pods avec une même adresse IP
statique. Un peut plus que le load balancer
On identifie les Pods par des labels (Selectors) qui seront les cibles du
load balancer
Peut faire du load balancing
Différents Types :
ClusterlP: expose le service à l'intérieur du cluster via une adresse
IP interne
Exemple : Un service de base de données accessible
uniquement par d’autres applications dans le cluster.
NodePort: expose le service via un port spécifique sur chaque
nœud du cluster
Exemple : Une application web simple accessible depuis votre
réseau local.
LoadBalancer: expose le service via un load balancer externe.
Exemple : Une application web en production accessible
publiquement avec plusieurs pods derrière le load balancer.
